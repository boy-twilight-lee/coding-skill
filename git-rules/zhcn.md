# Git 提交规则

本文是 [SKILL.md](SKILL.md) 的中文翻译，便于阅读和对照。

## 适用范围

生成、编辑、审查 Git 提交信息，或执行需要填写提交信息的提交操作时，应用本技能。仅以只读方式查看 Git 状态、日志或差异，不需要应用本技能。本技能约束提交信息，不代表获得提交、推送或改写历史的授权。

详细示例按本文的主要章节分类存放在 `references/` 中。编写或审查相关模式前，只阅读对应的参考文件。示例用于解释规则，不能覆盖用户的明确要求或仓库有意采用的约定。

## 工作流程

1. 能访问仓库时，检查仓库说明、提交信息校验配置和近期提交，了解已有的 scope、语言及格式约定。用户的明确要求优先。

2. 为即将执行的提交编写信息时，以暂存区差异为事实依据。仅根据用户描述起草时，不能声称已检查差异或完成验证。

3. 每次提交聚焦一个清晰易懂的目的。相关实现、测试和文档可以放在同一次提交中，标题应体现主要目的。对于无关的功能和修复，应建议拆分，不要自行调整用户的暂存区。

4. 检查提交类型是否符合实际行为、摘要是否准确、语言是否符合中文优先及其例外，以及是否识别了破坏性变更。不要把新增行为描述为纯重构。

5. 用户只要求提交信息时，提供可直接复制的文本。实际执行提交时，遵守用户授权和仓库要求。

## 语言与格式

确定中文优先的措辞、英文例外、摘要清晰度或标题语法时，阅读[语言与格式示例](references/language-and-format-examples.md)。

1. 使用 Conventional Commits 格式：

   ```text
   <type>[可选 scope][可选 !]: <中文摘要>

   [可选正文]

   [可选页脚]
   ```

2. 摘要和正文优先使用中文。仅在用户明确要求、仓库要求、提交历史持续采用纯英文，或必须保留原始技术术语时使用英文。Git、API、OAuth、TypeScript 以及代码标识符保留原文，不要强行翻译。中文信息中出现英文术语，并不意味着整条信息都必须改用英文。

3. `type` 使用小写英文。可选的 `scope` 使用简短、稳定的模块名，优先沿用项目约定，如 `auth`、`user` 或 `api`。冒号后留一个空格。

4. 用简洁、体现动作的摘要描述实际变化，例如 `修复登录后跳转失败`。避免 `修改代码`、`更新内容` 等含糊描述，避免夸大，不要在末尾加句号。摘要保持单行且简短，但不要为了任意长度限制牺牲准确性。

5. 仅在需要说明原因、行为影响或迁移方式时添加正文，并与标题空一行。问题页脚遵循仓库约定，如 `Refs: #123` 或 `Closes: #123`。只引用已知且真实存在的问题，仅在变更确实解决问题时使用 `Closes`。

## 提交类型

选择类型、区分功能与重构、归类 CSS 改动，或判断无关改动是否应分开提交时，阅读[提交类型示例](references/commit-type-examples.md)。

1. 根据实际变更的主要目的选择类型。新增面向用户的功能使用 `feat`；修复错误行为使用 `fix`；保持行为不变的结构调整使用 `refactor`；文档改动使用 `docs`。

2. 对应目的明确时，使用 `perf`、`test`、`build`、`ci`、`style`、`chore` 或 `revert`。不要把所有维护性改动都归为 `chore`。

3. `style` 仅用于不改变行为的代码格式调整。CSS 显示问题修复使用 `fix`；新增界面功能使用 `feat`。

## 正文与破坏性变更

解释原因、记录迁移、标记不兼容改动或关联已知问题时，阅读[正文与破坏性变更示例](references/body-and-breaking-change-examples.md)。

1. 正文细节必须基于实际改动。不要照搬示例中缺乏事实支持的行为描述。

2. 确实存在不兼容变更时，在类型或 scope 后添加 `!`，并通过 `BREAKING CHANGE:` 页脚说明影响和迁移方式。标记保留英文，说明优先使用中文。

3. 保持兼容性的普通内部重构，不要标记为破坏性变更。
