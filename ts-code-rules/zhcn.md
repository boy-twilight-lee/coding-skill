# TypeScript 代码规则

本文是 [SKILL.md](SKILL.md) 的中文翻译，便于阅读和对照。

适用范围：编写、修改、重构、审查、调试或补全 TypeScript、TSX、使用 TypeScript 的 Vue 脚本块，以及基于 TypeScript 的项目架构时，必须遵守本技能规定的编码、类型组织、导入、异步、常量、源码分层、格式与兼容性标准。

处理 TypeScript 或 TSX 时，应用下列所有相关规则。保留项目有意采用的不同约束，改动限于用户请求的范围。

详细示例按本文的主要章节分类存放在 `references/` 中。编写或审查相关模式前，只阅读对应的参考文件。示例用于解释规则，不能覆盖仓库已建立的约定。

## 工作流程

1. 修改或审查 TypeScript 前，阅读仓库说明，检查受影响的模块、公共调用方、附近的类型，以及相关 `tsconfig`、包脚本、lint、格式化和测试配置。进行兼容性决策前，确认实际运行环境和目标浏览器。

2. 确定任务涉及的规则章节，操作前阅读对应示例。Vue 单文件组件中的 TypeScript 同时遵守 `vue-code-rules`；同一次修改涉及 Vue 样式块时，还需遵守 `css-code-rules`。

3. 保持请求范围之外的公共契约和现有行为。如果本地约定与规则冲突，遵守更高优先级的指令及仓库有意采用的约束，不要扩大为无关迁移或清理。

4. 修改后，逐项对照相关章节检查差异。运行能够覆盖改动的最小检查，如仓库的定向格式化、TypeScript 检查、lint 和相关测试。避免执行会重写无关文件的命令。无法执行相关检查时应说明限制，不能仅凭编译或格式化通过就认定正确。

## 代码质量

确定改动范围、抽象、清理、声明注释、回调注释、内部注释或空行时，阅读[代码质量示例](references/code-quality-examples.md)。

1. 改动仅限于请求的功能或缺陷。保留现有注释，不要顺手格式化、重命名、调整导入顺序或重写无关代码。

2. 避免不必要的抽象。简单且只使用一次的逻辑保持内联；仅因真实复杂度、复用或明确职责边界而提取函数、类或 composable。

3. 清除属于当前改动范围的未使用导入、变量、函数、类型、临时调试代码、过时注释、冗余别名和只做转发的包装函数。

4. 为每个声明的变量和常量添加简洁注释，包括 `const`、`let`、类字段、响应式状态、ref、计算值和解构绑定。注释放在声明正上方，解释业务用途或状态含义，不要只重复名称或语法。注释使用中文，除非项目明确要求其他语言、必须准确引用外部协议或第三方术语，或中文会降低技术含义的准确性。导入、函数参数和仅用于类型的声明不需要单独的变量注释。Vue 单文件组件中，`vue-code-rules` 的编译器宏例外优先，不要仅为满足本条给编译器宏添加声明注释。

5. 为每个函数、方法、composable、回调、事件处理器和生命周期钩子添加简洁注释，放在声明或定义正上方，说明职责、副作用或返回含义。内联回调仅在具有独立职责、真实复用，或具体的测试、可读性收益时才提取为带注释的具名函数。仅在一处注册、只是延续当前操作或 API 流程的回调，只要相邻注释能清楚说明，就保持内联。不要仅因回调较长而拆出只使用一次的处理函数。

6. 函数或方法内部只注释关键业务逻辑、不直观的转换、重要分支、副作用和错误处理。不要逐句注释或重复显而易见的实现细节。即使实现明显，第 4、5 条要求的声明级注释仍必须保留。

7. 不要仅为获得名称或注释目标而引入、保留冗余代码。禁止只调用并返回另一个函数的转发函数；禁止没有独立职责、却拆散连续流程的一次性回调包装；禁止不提供业务含义、复用、类型收窄或可读性收益的一次性中间变量；禁止唯一调用方、框架或经核实的 API 契约已保证成立的重复校验和守卫。应直接内联底层表达式、回调或调用。只有具有独立职责或具体正确性收益时，才保留包装、中间值、回调提取或守卫；注释不能成为冗余结构的理由。

8. TypeScript 或 TSX 中不得保留无意义空行。只有确实分隔不同逻辑区域时，才允许使用一个空行。禁止连续空行、文件开头或结尾的空行、代码块开闭边界内侧的空行、必需注释与声明之间的空行，以及紧密相关的导入、声明、语句、对象成员、JSX 节点或类型成员之间的空行。真正独立的逻辑组之间最多保留一个有意设置的空行，删除所有不能改善结构可读性的空行。

## 导入与源码分层

确定统一导出入口、导入顺序、类型位置、源码归属、私有常量或是否提取常量时，阅读[导入与源码分层示例](references/imports-and-source-layers-examples.md)。

1. `src` 下的每个一级目录都必须通过 `index.ts` 暴露公共内容，`src/assets` 和 `src/pages` 除外。优先通过这些统一入口导入，避免深层路径引用；禁止向上跨越两层或更多父目录，使用项目配置的路径别名。

2. 导入顺序为：第三方库、仅作类型使用的依赖、其他内部依赖、组件。类型也使用标准 `import` 声明以保持可读性，禁止类型专用导入声明或内联类型修饰符。类型依赖组中，组件或模块私有类型排在共享类型之前。Vue 代码先执行 `vue-code-rules` 要求的 Vite 自动导入检查：已覆盖的 `vue` 或 `vue-router` API 不要显式导入；仅对仍需导入的 API 应用上述排序。

3. `.d.ts` 声明放在 `src/type`。复杂或可复用的组件私有类型放在所属组件旁的类型模块中；简短的 props 字面量可以内联，以改善可读性。不要在 Vue `<script setup lang="ts">` 中声明非简单的 interface 或类型别名。

4. 接口端点声明放在 `src/apis`；请求客户端配置、响应归一化和通用无状态辅助函数放在 `src/utils`。应用级不可变值放在 `src/constants`，Pinia 状态放在 `src/store`，路由定义与守卫放在 `src/router`。

5. 页面或组件私有的 `constants/`、`type/` 目录放在所属对象旁边。只有存在明确的跨页面使用方时，才提升到 `src/constants` 或 `src/type`。不要将状态值、选项、枚举或魔法数字散落在模板和实现分支中。

6. 不要机械提取常量。只使用一次、在使用位置含义清楚且不太可能独立变化的值或配置，保持内联。不要仅为替代内联字面量而提取一次性的组件库配置。仅在提供真实复用、集中共享事实来源、赋予不明确的值重要业务含义，或需要独立维护时，才创建具名常量。

## 异步与兼容性

处理 Promise、错误、发起后无需等待的调用约定、新 API、目标环境支持或最终格式检查时，阅读[异步与兼容性示例](references/async-and-compatibility-examples.md)。

1. 优先使用 `await`，而不是 `.then()`，并通过 `try/catch` 处理异步错误。不要使用一元 `void` 丢弃 Promise；应等待并处理它，或仅在明确约定调用方同步发起且无需等待的场景下调用。

2. 优先使用稳定、广泛支持的 ES6 API。引入更新的 JavaScript 或浏览器 API 前，确认目标环境支持，或使用项目认可的 polyfill。

3. 仅使用仓库配置的 Prettier 格式化本次修改的文件，再对照规则和本地既有约定检查结果。
