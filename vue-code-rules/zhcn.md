# Vue 代码规则

本文是 [SKILL.md](SKILL.md) 的中文翻译，便于阅读和对照。

适用范围：编写、修改、重构、审查、调试或补全 Vue 项目代码时，必须遵守本技能规定的 Vue 3 模板、组件结构、组件命名、组合逻辑及应用架构标准，包括 `.vue` 组件、composable、页面、布局和组件目录。

处理 Vue 项目代码时，应用下列所有相关规则。保留项目有意采用的不同约束，改动限于用户请求的范围。Vue 文件内涉及 TypeScript 或样式修改时，还需分别应用 `ts-code-rules` 或 `css-code-rules`。

详细示例按本文的主要章节分类存放在 `references/` 中。编写或审查相关模式前，只阅读对应的参考文件。示例用于解释规则，不能覆盖仓库已建立的约定。

## 工作流程

1. 修改或审查 Vue 代码前，阅读仓库说明，检查受影响的组件、最近的相关组件，以及相关构建、lint、格式化和 TypeScript 配置。应用本技能的默认规则前，先识别项目有意采用的本地约定。

2. 确定任务涉及的规则章节，操作前阅读对应示例。Vue 单文件组件涉及 TypeScript 或样式修改时，同时加载并应用 `ts-code-rules` 或 `css-code-rules`；不能认为本技能替代了它们。

3. 实现与清理均限于请求范围。如果本地约定与规则冲突，遵守更高优先级的指令和仓库有意采用的约束。除非任务明确要求改变周边模式，否则保留原有模式。

4. 修改后，逐项对照相关章节检查差异。运行能覆盖改动的最小检查，例如仓库的定向格式化、lint、Vue 类型检查和相关测试。避免执行会重写无关文件的命令。相关检查无法运行时，应说明限制，不能仅凭格式化或目视检查认定正确。

## 模板规则

确定单文件组件块顺序、列表渲染、模板表达式、组件标签、插槽、DOM 深度或语义元素时，阅读[模板示例](references/template-examples.md)。

1. Vue 单文件组件块严格按 `<template>`、`<script>`、`<style>` 排列。不得将 script 放在 template 前，也不得将 style 放在 script 前。

2. 重复 UI 使用结构化数据配合 `v-for` 渲染，并提供稳定且唯一的 key。只要条目标识可能变化，就不得使用数组下标作为 key。

3. 业务转换和非简单条件不要放在模板中。将其组织为有明确名称的计算状态或函数，使模板保持为易读的 UI 声明。

4. 自定义组件标签使用 kebab-case。没有插槽或子内容的组件使用自闭合标签。

5. 组件根节点和模板层级应与业务职责对应。需要明确扩展点时使用具名插槽；不要仅为满足抽象约定而添加包装元素。

6. 避免无意义 DOM。目标元素可以直接设置样式或布局时，不要仅为样式或布局再嵌套元素。保持 DOM 层级浅、节点数量少。只有具有明确且独立的布局、定位、动画、交互或分组职责时，才添加容器，并使用能表达该职责的名称。

7. 业务组件 DOM 中，块级分组优先使用 `div`，行内内容使用 `span`，图标占位使用 `i`。尽量减少语义标签，纯视觉强调通过 CSS 类实现。仅在顶层页面结构、SEO 或无障碍要求明确需要时，有意识地使用语义元素。

8. 元素有多个 class 来源时，合并到一个绑定的 `:class` 数组中。固定类名字符串、可复用 class 值和条件 class 对象都放在该数组中；必要时分行，避免属性过长难读。同一元素不要将 class 分散在 `class` 和 `:class` 中，也不要拼接很长的 class 字符串。单个静态类可保留在 `class` 中；只有一个动态对象或值时，无需额外包成数组。

## 空行规则

判断空行是否确实分隔单文件组件或逻辑区域时，阅读[空行示例](references/blank-line-examples.md)。

1. Vue 文件的模板、脚本和样式块中，都不得保留无意义空行。只有一个空行确实能分隔不同逻辑区域时，才允许使用。禁止连续空行、单文件组件块内部开头或结尾的空行、代码块开闭边界内侧的空行、必需注释与其声明之间的空行，以及紧密相关的语句或标记节点之间的空行。

2. 顶层单文件组件块之间，或真正独立的逻辑组之间，最多保留一个有意设置的空行。删除不能使组件结构更易理解的空行。

## 脚本结构规则

排列 Vue 导入、编译器宏、运行时声明，或判断 Vue、Vue Router API 是否需要显式导入时，阅读[脚本结构示例](references/script-structure-examples.md)。

1. 所有 Vue 编译器宏调用都放在 `<script setup>` 的脚本作用域，绝不能放进函数、回调、条件、循环或其他嵌套代码块。除 `defineExpose` 外，所有宏都放在必要导入之后的第一个声明组中，并位于普通运行时状态、计算值、watcher、生命周期调用和函数之前，包括 `defineOptions`、`defineProps`、`withDefaults`、`defineModel`、`defineEmits` 和 `defineSlots`。`defineExpose` 必须放在 `<script setup>` 最底部，位于所有声明、watcher、生命周期调用和其他可执行语句之后；脚本块内不得再有任何内容位于其后。

2. 添加来自 `vue` 或 `vue-router` 的显式导入前，检查 `vite.config.*`，以及其中引用的所有控制自动导入的 Vite 插件或共享配置。具体 API 已被当前生效的自动导入配置覆盖时，直接使用，不要在改动代码中添加或保留冗余显式导入。API 未覆盖、配置对目标不生效，或无法确认覆盖情况时，显式导入。Vite 配置是事实依据；仅有依赖声明、生成的类型声明文件、相邻代码或全局类型，不能证明运行时自动导入已生效。

## 脚本注释规则

为声明、回调、watcher、生命周期钩子、业务分支或副作用添加说明时，阅读[脚本注释示例](references/script-comment-examples.md)。

1. 每个 Vue `<script>` 块中，所有声明的变量或常量正上方都要添加简洁注释，包括响应式状态、ref、计算值、解构绑定和类字段。说明业务用途或状态含义，不要只重复标识符。注释使用中文，除非项目明确强制其他语言、外部协议或第三方术语必须准确引用，或中文会降低技术含义的准确性。导入、函数参数和仅用于类型的声明不需要单独的变量注释。Vue 编译器宏同样是明确例外：`defineProps`、`withDefaults(defineProps(...))`、`defineEmits`、`defineExpose`、`defineOptions`、`defineSlots` 或其他编译器宏的正上方，绝不添加声明注释，包括接收宏返回结果的变量或解构声明。

2. 每个函数、方法、composable、回调、事件处理器、watcher 回调和生命周期钩子正上方，都要添加简洁注释，说明职责、副作用或返回含义。如果包含内联回调的 API 调用、watcher、生命周期调用、对象属性或声明正上方的紧邻注释，已能明确描述该回调，即视为注释充分；不要仅为满足规则而在表达式内部再插注释。内联回调仅在具有独立职责、真实复用，或具体测试、可读性收益时，才提取为带注释的具名函数。只在一个注册位置使用、只是延续当前操作、watcher、生命周期或 API 流程的回调，应保持内联。不要仅因回调较长，就将连续流程拆成只使用一次的 `handle*` 或 reset 函数。

3. 函数和方法内部，只注释关键业务逻辑、不直观的转换、重要分支、副作用和错误处理，不要逐句注释。这些声明级注释规则对 JavaScript 和 TypeScript Vue 脚本均为强制要求；TypeScript 脚本还需遵守 `ts-code-rules`。

4. 不要仅为获得名称或注释目标而引入、保留冗余代码。禁止只调用并返回另一个函数的转发函数；禁止无独立职责、却拆散连续流程的一次性回调包装；禁止不提供业务含义、复用、类型收窄或可读性收益的一次性中间变量；禁止唯一调用方、Vue 或被调用 API 经核实的契约已保证成立的重复校验、守卫。应直接内联底层表达式、回调或调用。只有具有独立职责或具体正确性收益时，才保留包装、中间值、回调提取或守卫；注释不能成为冗余结构的理由。

## 组件结构规则

确定组件拆分、composable 提取、命名、目录布局或私有归属时，阅读[组件结构示例](references/component-structure-examples.md)。

1. 组件混合了独立职责、存在真实可复用的内聚单元，或单文件难以维护时，应进行拆分。独立 UI 职责提取为子组件，内聚的有状态行为提取为 composable。紧密耦合的模板、状态和操作保持在一起；不要仅为减少文件大小，拆分琐碎代码、连续流程或任意行区间。

2. 可复用的状态、副作用和业务行为提取到 composable 中。状态、操作或派生数据需要跨越多个组件层级传递并频繁更新时，提供专门的 `use**Context` composable，使用 provide/inject，避免继续逐层透传 props 和 emits。

3. Vue 组件文件名和自定义标签使用 kebab-case。composable 文件名使用 kebab-case，但 `hooks/` 目录内的 hook 文件使用 camelCase。

4. `src/pages`、`src/views`、`src/components` 下的每个一级页面或组件，以及项目已有的对应终端目录（如 `pages-pc`、`components-pc`）中的一级单元，都必须使用 kebab-case 文件夹，即使实现简单也不例外。每个单元必须包含 `index.vue` 和导出该组件的 `index.ts`。下述单文件例外只适用于所属对象的私有 `component/` 目录，不能据此创建 `src/components/user-avatar.vue` 或 `src/views/candidate-list.vue`。

5. 页面、视图或组件所属的私有 `component/` 目录内，模板、脚本和样式能在一个单文件组件中保持内聚的简单子组件，直接使用 kebab-case 文件名，如 `empty-hint.vue`。不要仅为形式统一，再创建子组件同名目录或独立的导出、样式文件。仅有 props、emits、短脚本或局部样式，不构成拆分私有子组件的理由。子组件确需有意义的配套文件，如提取的逻辑、样式、私有子组件或 hook 时，再使用子组件同名目录，并同时包含 `index.vue` 和 `index.ts`。

6. 每个采用文件夹管理的 Vue 组件，包括页面、视图入口和私有子组件，都必须提供 `index.ts`，重新导出 `index.vue` 的默认组件。仅在需要时导出公共类型或其他预期公开的 API。使用方通过导出入口引用组件目录，不直接导入内部 `index.vue`；项目使用更上层的统一导出入口时，继续保留该入口。`index.ts` 只作为导出入口，不用于容纳提取的 setup 或业务逻辑。

7. 普通 setup 逻辑和局部样式默认保留在单文件组件中。仅当逻辑、类型或常量具有明确职责、复用或维护收益时，才提取到职责集中的文件。只有独立样式确有必要且项目支持 Less 时，才使用 `index.less`。强制组件目录和 `index.ts`，并不代表必须有独立样式文件，也不要求凑齐 `index.vue`、`index.ts`、`index.less` 三件套。

8. 组件私有子组件放在所属组件目录的 `component/` 中，私有 composable 放在 `hooks/` 中。每一层嵌套都独立应用私有子组件规则。每个 `.vue` 文件总行数不超过 1000 行，按职责拆分，不要机械拆分。私有单文件子组件成长为目录，或提升为一级共享组件时，添加必需的 `index.ts`，并更新受影响的导入和自动组件注册。不要仅为统一目录形式而迁移无关组件。

## 复杂组件上下文规则

实现或审查任何 `use**Context` composable、提供方、注入方、回退值或使用方前，阅读[复杂组件上下文示例](references/complex-component-context-examples.md)。

1. 每个名为 `use**Context` 的 composable，都实现为只返回两个方法的上下文门面：所属组件调用的 `provide()`，以及后代调用的 `inject()`。文件放在所属页面或组件的 `hooks/` 目录中，定义模块级且包含业务限定含义的上下文 key。

2. 所有归属于上下文的响应式状态、计算值、模板 ref、watcher、副作用和操作，都在 `provide()` 内创建。将公开值组装成一个 `context` 对象，把同一个对象传给 Vue 的 `provide`，并返回它，让所属组件与后代共享同一套 API 和实例。不要将 `use**Context` 实现为模块级响应式单例，也不要拆成互不关联的独立提供、注入函数。

3. `inject()` 使用 Vue 的 `inject`，并提供完整回退对象。回退对象的公开字段必须与所提供的 `context` 完全一致，包含安全的空 ref 和类型正确的空操作函数。不得遗漏已提供字段、增加仅注入侧存在的字段，或通过不安全的部分类型断言隐藏不匹配。

4. 上下文只在所属复杂组件子树中使用：所属组件调用一次 `use**Context().provide()`，后代调用 `use**Context().inject()`。不要在多个后代中调用 `provide()`，也不要将此模式用于应用全局状态。

## 应用架构

放置页面、组件、布局、私有模块、不同终端目录、依赖或工具函数时，阅读[应用架构示例](references/application-architecture-examples.md)。

1. 路由级编排放在项目既有的 `src/pages` 或 `src/views` 中，以及存在时的对应终端目录（如 `src/pages-pc`）中。不要仅为改名而引入一套竞争性的页面目录。可复用的展示与交互单元放在 `src/components` 及存在时的 `src/components-pc`。一级页面和组件使用包含 `index.vue`、`index.ts` 的目录。页面框架放在 `src/layout`。

2. 页面私有的 `component/` 和 `hooks/` 目录放在页面旁边。只有存在明确跨页面使用方时，才将代码提升到 `src` 层级目录。

3. 项目已区分移动端与 PC 页面、组件目录时，保留这种区分。除非请求明确要求共享行为，否则不要通过运行时设备判断分支合并它们。

4. 手写某项能力前，先检查项目已安装的依赖，再查看成熟的第三方库。现有依赖或成熟库已经能可靠实现需求时，应直接使用，不要自建替代品。只引入积极维护且许可证、使用条款已核实适合安全商用的包。不得使用许可未知、受限、copyleft、source-available，或其他在许可、来源上存在商用风险的包。

5. 凡可在当前调用点之外复用的无状态工具函数，都提取到 `src/utils`。按业务领域或技术能力组织为职责集中的模块：已有匹配模块时扩展它，否则创建名称明确的模块。公共工具通过 `src/utils/index.ts` 导出。不要直接在统一导出文件中放实现，不要把可复用辅助函数留在 Vue 组件或 composable 中，也不要把无关函数塞进名称模糊的大杂烩文件。
