# Vue Code Rules

Apply every rule relevant to the Vue code created, changed, or reviewed by the task. These are requirements, not suggestions inferred from nearby code. Existing code is context rather than a waiver. Do not migrate untouched code solely to normalize it; fix an existing violation when it is in the changed lines, is necessary for the requested behavior, or prevents the changed code from complying.

Higher-priority instructions override this skill. Repository configuration or conventions override a rule only where that rule explicitly delegates the decision to project configuration. If a mandatory rule cannot be followed, make the smallest necessary deviation and report the exact conflict instead of silently skipping it.

Core rules live in this entrypoint as a safety baseline; this does not make reference loading optional. References add detailed decision boundaries and review checklists, with examples only where concrete contrasts improve the decision.

In examples, `<zh: ...>` marks placeholder content for a Chinese comment. Replace the marker with concise Chinese text when the surrounding rule calls for that comment; never copy the marker into project code. Required business documentation still applies when identifiers are clear; omit only comments that add no responsibility, scope, contract, or rule information.

Keep positive and negative examples free of comments unless a comment is necessary to demonstrate a comment rule, comment spacing/placement, or a non-obvious constraint essential to that example. Put ordinary explanations outside code fences. Focused examples may omit unrelated documentation to show their target rule clearly; this example-writing policy does not waive business-comment requirements in actual project code.

## Core Rules

1. Keep present SFC blocks in `<template>`, `<script>`, `<style>` order and omit empty blocks. Use kebab-case custom tags, and self-close components without content.
2. Implement the required functionality with as few DOM nodes and nesting levels as possible. Do not add unnecessary nodes or meaningless wrappers. Add a wrapper only when existing elements cannot implement the required behavior or layout directly, and keep any necessary structure minimal. Prefer common HTML tags such as `div`, `span`, `i`, `button`, and `input` throughout implementations. Do not use uncommon tags or landmark/sectioning containers such as `main`, `nav`, `aside`, `section`, `article`, `header`, and `footer`. Keep interactions on appropriate common native controls, and never invent tags such as `dataset` or `landmark`. Unless the user explicitly requests accessibility compatibility, do not add unrelated accessibility attributes to any DOM tag, including `aria-*`, accessibility-only `role`, or accessibility-only `tabindex`.
3. Order attributes on each template opening tag as directives first, then `v-bind` bindings, literal text attributes, plain boolean attributes, and finally events. Give `v-if` and `v-show` equal highest directive priority without ranking one above the other; keep `v-else-if` or `v-else` in the same leading group on its corresponding branch, ahead of other directives such as `v-for`, `v-model`, and slot directives. Treat `:` and `v-bind` forms, including bound booleans, class, and style, as bindings; treat `@` and `v-on` forms as events. Preserve meaningful order within each group, spread override semantics, and conditional sibling adjacency; do not reorder template children to enforce attribute order.
4. Combine multiple class sources in one `:class` array. Do not split the same element across `class` and `:class` or build long concatenated class strings.
5. Use blank lines only between genuinely separate SFC blocks or logical regions. Never use consecutive, leading, trailing, block-edge, comment-separating, or tightly-coupled blank lines.
6. Verify Vite auto-import configuration before adding Vue or Vue Router imports. Omit an explicit import only when the exact runtime API is covered by active configuration.
7. Keep compiler macros at `<script setup>` scope. Put macros other than `defineExpose` immediately after imports and before runtime logic. Put `defineExpose` last unless top-level `await` requires exposed bindings to be initialized and exposed before the first await.
8. Document major business state and computed values, actions and event handlers, prop/event/model/slot contracts, business watchers, lifecycle work, and key interaction or transformation stages with concise Chinese comments even when their names are clear. Put watcher and lifecycle responsibility comments above the containing call, and explain distinct internal rules above their own cohesive blocks. Document contract members instead of adding generic compiler-macro declaration comments. In multi-region templates, annotate major business regions and significant rendering or interaction rules without labeling every node. Naming, simple syntax, or a compatibility comment elsewhere does not replace this coverage.
9. Use kebab-case component files, directories, and tags. First-level pages and components use directory form with `index.vue` and `index.ts`; only simple private children may remain single files. Restrict the owner root to those entries, optional `component/`, `constants/`, `hooks/`, `type/`, and one extracted-style form: `index.less` for a single stylesheet or `style/` for multiple stylesheets, never both. Preserve the existing stylesheet language's equivalent extension. Do not invent unrelated component directories or loose helper files. Group cohesive owner-specific functional helpers in a focused utility hook under `hooks/`; place genuinely shared stateless utilities in the project's established `utils` layer. Create optional entries only when needed. A private child that requires an extracted stylesheet must use directory form. Keep `index.ts` declarative: forward the default component and the methods, components, types, or subdirectory modules that external consumers actually need. When another component needs the instance type, export a named instance type from this public entry, such as `export type DrawerInstance = InstanceType<typeof Drawer>`.
10. Keep each `.vue` file at or below 1000 lines: consider child components for large or deeply nested templates, responsibility-focused hooks for large scripts, and stylesheet extraction under `css-code-rules` for large styles. Update public entries, consumers, and component discovery after splitting or moving, without migrating unrelated components. Split by actual responsibility rather than arbitrary line chunks; preserve state and lifecycle ownership, component contracts, and stylesheet scope.
11. Every scenario involving Vue `provide` or `inject` must follow the fixed context pattern in [Provide/Inject Context Pattern](references/complex-component-context-examples.md), regardless of subtree depth or how many values are shared. Use an owner-scoped `use**Context` facade returning exactly `provide()` and `inject()`. Create state inside `provide()`, provide and return the same complete context object, and make `inject()` return an exactly matching safe fallback. The complete example defines the required implementation structure, not an optional illustration.

## Required Reference Loading

Loading this entrypoint is not the complete workflow. After the initial repository inspection and before making implementation or review judgments, map every affected concern to the list below and read each matching reference in full. Every task covered by this skill must open at least one reference. When no route seems to match, read the closest reference instead of proceeding with only this entrypoint. Do not merely mention or summarize a reference without opening it. When uncertain whether a reference applies, read it. References are authoritative requirements, not optional background.

Each core rule owns one reference below. When a task also touches another rule, load that rule's reference as well.

- Rule 1: Read [Template Examples](references/template-examples.md) when deciding SFC block order, component tags, or slots.
- Rule 2: Read [DOM Structure Examples](references/dom-structure-examples.md) when deciding DOM minimality, wrapper necessity, common tag selection, prohibited uncommon and landmark elements, or whether accessibility attributes are within the user's requested scope.
- Rule 3: Read [Template Attribute Order Examples](references/template-attribute-order-examples.md) when adding, changing, or reviewing attributes and directives on template tags, including conditional priority, bindings, text attributes, boolean flags, events, and order-sensitive spreads.
- Rule 4: Read [Class Binding Examples](references/class-binding-examples.md) when an element combines static, reusable, or conditional class sources.
- Rule 5: Read [Blank Line Examples](references/blank-line-examples.md) when deciding SFC block spacing, template whitespace, or JavaScript-script whitespace. TypeScript-script whitespace belongs to `ts-code-rules`; style-block whitespace belongs to `css-code-rules`.
- Rule 6: Read [Auto-Import Examples](references/auto-import-examples.md) when deciding whether Vue or Vue Router APIs need explicit imports based on the active Vite auto-import configuration.
- Rule 7: Read [Compiler Macro Examples](references/compiler-macro-examples.md) when placing compiler macros, ordering component contracts and runtime declarations, or exposing initialized bindings around top-level `await`.
- Rule 8: Read [Script Comment Examples](references/script-comment-examples.md) for business-state, contract, watcher, lifecycle, and template-region comment coverage and placement, and for the generic script baseline in JavaScript SFCs. For TypeScript SFCs, `ts-code-rules` owns the generic declaration, callback, internal-comment, and redundancy rules.
- Rule 9: Read [Component Structure Examples](references/component-structure-examples.md) when deciding component naming, the fixed owner directory structure, helper/hook ownership, mutually exclusive style-file layouts, public entries and externally needed submodules, exported instance types, or private-file organization.
- Rule 10: Read [Component Decomposition Examples](references/component-decomposition-examples.md) when deciding file-size limits, template/script/style split triggers, responsibility boundaries, or post-split verification.
- Rule 11: Read [Provide/Inject Context Pattern](references/complex-component-context-examples.md) before implementing or reviewing any Vue `provide` or `inject` scenario, including its facade, key, fallback, and consumers. Follow its complete fixed example.

## Working Process

1. Before changing or reviewing Vue code, read the repository instructions and inspect the affected component, its nearest related components, and the relevant build, lint, formatter, and TypeScript configuration. Use that evidence for configuration-dependent decisions and to avoid unnecessary unrelated churn.

2. Complete the required reference loading before acting. When a Vue SFC contains TypeScript or style changes, load and apply `ts-code-rules` or `css-code-rules` as well; do not assume this skill replaces them.

3. Keep implementation and cleanup within the requested scope. Do not copy a local violation into new or changed code merely to preserve visual consistency. When an explicit higher-priority instruction conflicts, follow it and document the smallest necessary exception.

4. After the change, inspect every changed Vue line against each applicable numbered rule and its reference checklist. Run the smallest available checks that exercise the changed Vue code, such as the repository's targeted formatter, lint, Vue type-check, and affected tests. Avoid commands that rewrite unrelated files. If a rule or check cannot be satisfied, report it explicitly instead of treating formatting or visual inspection as proof of correctness.
